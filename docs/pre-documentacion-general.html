Nombre por decidir

Aplicación web —y posteriormente Android— que reúne en un solo lugar la información sobre el Fenómeno El Niño publicada por los organismos que lo monitorean, la interpreta para el usuario común y la combina con reportes enviados por los propios usuarios.

01  Problema y enfoque

Información dispersa y poco accesible para el ciudadano

La información sobre El Niño existe, pero está repartida entre organismos globales (NOAA, NASA, OMM), regionales (CIIFEN) y nacionales (ENFEN, SENAMHI, IGP), en formatos distintos —APIs geoespaciales, PDFs técnicos, boletines e índices numéricos— y redactada para especialistas. El usuario común no dispone de un lugar único donde consultar, de forma rápida, qué está ocurriendo y qué medidas tomar.

El proyecto atiende dos carencias: el acceso (centralizar e interpretar los datos oficiales) y el detalle local (la información a nivel de calle o barrio que los organismos no registran, aportada por los propios usuarios).

Aporte diferenciador (propuesta principal)

Un método para estimar la confiabilidad de los reportes ciudadanos combinando la corroboración entre usuarios (modelo similar a Waze) con la validación cruzada contra los datos hidrometeorológicos oficiales de la zona. La hipótesis de trabajo es que ese cruce reduce los falsos positivos frente a la corroboración por votos por sí sola.

Enfoques alternativos, en caso de reorientar el foco del proyecto:

  • Interoperabilidad: un modelo común para integrar fuentes heterogéneas de monitoreo del ENSO (índices, geoespacial y boletines).
  • Comunicación de riesgo: generación de lenguaje natural (NLG) que traduce indicadores técnicos a un mensaje comprensible sin alterar el dato.

Decisión pendiente: definir cuál de los tres enfoques es el central. El resto del documento asume el primero (validación cruzada).

02  Alcance por fases

Dos productos distintos, en fases separadas

El sistema combina dos componentes de naturaleza diferente: una plataforma de datos (desarrollo predecible) y una capa social en tiempo real (que concentra la mayor parte del riesgo técnico y de moderación). No se recomienda desarrollarlos en paralelo. Cada fase constituye un entregable independiente.

v1 · MVP

Plataforma de datos + mapa

Web, solo lectura. Constituye un producto completo por sí solo.

  • Mapa interactivo con anomalías de SENAMHI (Leaflet + GeoJSON)
  • Titular del estado de alerta oficial (ENFEN)
  • Gráficos de índices (ONI de NOAA, ICEN del IGP)
  • Resumen en lenguaje natural con LLM controlado
v2

Reportes ciudadanos

Cuentas y reportes estructurados sobre el mapa.

  • Tipo de incidente, ubicación, foto
  • Confirmación por votos de vecinos
  • Cruce con datos oficiales (validación central)
  • Sin chat libre todavía, más fácil de moderar
v3

Tiempo real + móvil

El componente de mayor riesgo; se aborda al final.

  • Chat en tiempo real, mensajes efímeros
  • Moderación (filtros + clasificador)
  • App Android (GPS nativo)

Si v2 o v3 se retrasan, v1 se mantiene como un producto terminado. El faseo reduce el riesgo frente a la fecha de entrega.

03  Arquitectura del sistema

Estructura general del sistema

El criterio de diseño es que cada organismo se integra mediante un conector aislado que normaliza sus datos a un modelo común. Así se pueden añadir fuentes de forma incremental sin afectar al resto, y el frontend recibe siempre el mismo formato, con independencia del origen.

El estado de alerta oficial lo publica ENFEN, no la API de SENAMHI. El catálogo GeoNetwork de SENAMHI corresponde a la Infraestructura de Datos Espaciales (metadatos y mapas) y es la fuente de los mapas; el nivel de alerta de El Niño Costero lo fija ENFEN.

Estrategia de adquisición

La mayoría de los organismos no ofrece una API pública documentada. La obtención de datos sigue un orden de preferencia, de la fuente más estable a la más frágil:

  1. API documentada o archivo abierto. NOAA publica el ONI como archivo de texto y SENAMHI expone la API de GeoNetwork. Es la vía preferente por su estabilidad.
  2. API interna detectada por inspección de red. Cuando una web carga sus datos mediante peticiones XHR/fetch sin documentar (caso probable de ENFEN e IGP), se identifica ese endpoint con las herramientas de red del navegador y se consume directamente. Devuelve datos estructurados y es más estable que raspar el HTML.
  3. Scraping de HTML o PDF. Último recurso, cuando no existe un endpoint de datos. Es el método más sensible a los cambios del sitio.

Consideraciones de uso responsable:

  • Cachear las respuestas y limitar la frecuencia de peticiones (rate limit) para no sobrecargar los servidores de origen.
  • Enviar un User-Agent identificable y revisar los términos de uso y el robots.txt de cada sitio.
  • Como las APIs internas no están documentadas y pueden cambiar sin aviso, cada fuente se implementa en un conector aislado con pruebas (ver sección 11).

05  Pipeline de mapas

Obtención y renderizado de los mapas de SENAMHI

El catálogo GeoNetwork de SENAMHI expone su API sobre CSW y Elasticsearch. Los mapas de anomalías se descargan como shapefiles dentro de un archivo .zip adjunto a cada registro. El pipeline los convierte a un formato que el navegador puede representar.

06  Capa de interpretación

Interpretación de los datos con el LLM

Esta capa aporta valor, pero también concentra riesgo: una aplicación que entrega información errónea sobre un peligro es peor que no tener aplicación. Por ese motivo la interpretación se divide en dos niveles:

  • Titular por reglas (determinista): el estado y los números provienen de lógica fija, no del modelo. Ejemplo: ICEN = +0.9 → "cálidas débiles". Es la información que se muestra de forma destacada y no depende del LLM.
  • Narrativa por LLM (opcional): el modelo redacta el párrafo explicativo recibiendo los números ya calculados en el prompt, con la instrucción de no introducir cifras nuevas. Traduce el lenguaje técnico; no genera hechos.

De este modo el LLM redacta la explicación, pero el dato de riesgo siempre es trazable a una fuente oficial.

El titular como semáforo

El estado de alerta se representa con color, además de texto, para facilitar su lectura rápida:

No activo / normal Vigilancia Alerta Alerta alta

Los niveles exactos se ajustan a la nomenclatura vigente de ENFEN; el color es semántico e independiente del color de acento de la interfaz.

07  Reportes ciudadanos y alertas falsas

Validación de reportes ciudadanos

La detección de reportes falsos es uno de los puntos más difíciles del proyecto. El enfoque no parte de un modelo de aprendizaje automático, sino de una estructura de validación por etapas. Cada reporte acumula señales de confianza en cadena; el cruce con los datos oficiales entra al final y ajusta el puntaje de confianza.

Otras medidas complementarias:

  • Rate limiting y un reporte por zona/tiempo para frenar el spam.
  • Mensajes efímeros por diseño: expiran, lo que limita el daño a largo plazo.
  • Botón de reportar siempre visible; moderación humana como última capa.
  • Filtro de chat (v3): lista de términos en español y rate limit primero; clasificador de toxicidad después.

Aviso legal y ético: la aplicación ofrece información comunitaria y no constituye un canal oficial de emergencias. Cada reporte debe incluir un aviso claro y derivar a los números de emergencia reales (105 / 116). Debe considerarse desde el diseño.

09  Modelo de datos

Entidades principales

Esquema mínimo que sostiene las tres fases. Los elementos geoespaciales (mapas y reportes) se almacenan con geometría PostGIS para permitir consultas por cercanía.

  • source — cada organismo/conector: nombre, tipo, última sincronización.
  • index_series — series de índices (ONI, ICEN): fuente, fecha, valor, categoría.
  • alert_state — estado oficial vigente de ENFEN: nivel, fecha, comunicado.
  • map_layer — mapas de SENAMHI: uuid, variable, fecha, GeoJSON, imagen de previsualización.
  • user — cuentas (v2): reputación, zona.
  • report — reportes ciudadanos (v2): tipo, geometría, foto, autor, puntaje de confianza, expira_en.
  • confirmation — votos de corroboración sobre un reporte (v2).

11  Riesgos y consideraciones

Riesgos identificados

  • Alcance excesivo. Es el mayor riesgo. Mitigación: el faseo descrito en la sección 02.
  • Fragilidad de las fuentes. Los PDFs y el HTML de los organismos cambian. Mitigación: conectores aislados con pruebas y uso del formato más estructurado disponible en cada caso.
  • Licencias y atribución. Cada organismo tiene términos de uso propios; deben revisarse y la fuente debe atribuirse de forma visible en cada dato.
  • Responsabilidad legal. Una aplicación de emergencias implica responsabilidad legal; requiere un aviso claro y no presentarse como canal oficial.
  • Desinformación mediante el LLM. Se mitiga con el diseño en dos niveles (sección 06).
  • Privacidad de la ubicación. Debe solicitarse permiso explícito y nunca exponerse la ubicación exacta de un usuario en el mapa público.
